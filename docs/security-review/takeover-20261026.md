## Changes and regression findings

- Saved-exit checking now recomputes its authorization commitment and matches every broadcast transaction and CPFP child byte-for-byte against the preserved signed plan. A valid plan cannot authorize different journal bytes.
- An intermediate-only exit package cannot release the recovery guard merely because all of its current transactions confirmed. It must contain a destination payout before it can be considered complete. Complete per-leaf economic verification still needs final SDK acceptance.
- Rechecking a previously confirmed refund/exit invalidates that old confirmation before fresh network work. If that work fails, the journal remains unresolved rather than retaining stale permission to spend. Continuation approvals expire after 60 seconds. Adopting an exit is refused while an outgoing payment is unresolved.
- Spark confirmation displays `paymentMethod.fee` from the prepared SDK quote. Missing, negative or unrepresentable fees disable Send and show an unknown fee rather than zero. Nonzero fees remain visible; there is no silent Lightning substitution or hardcoded zero-fee result.
- Encrypted exit snapshots now resolve saves only after the IndexedDB transaction commits. Key creation uses a serialized compare-and-insert transaction so concurrent first writers cannot replace each other's key. Reading a damaged backup never creates a replacement encryption key.
- The rollback fixture now exercises the actual encrypted exit-backup store in addition to the previous vault, journals, exit plans and disposable SDK-state sentinel. Added real-browser tests force simultaneous key creation and an abort after the write request succeeds.
- Main's network-selection, localization, navigation and website changes are integrated. Recovery screens retain their existing four translations with an explicit English fallback for the newly supported languages. Full security-copy translation acceptance is still pending.
- The browser-engine matrix now runs on every candidate push and saves structured test reports. Bitcoin regtest tests the committed source instead of running a source-rewriting integration script first.

## Remaining work that prevents release

1. **New and rebuilt exits:** saved signed continuations and refunds are available through narrow controllers, but browser `recoverFunds`/new-plan and rebuilt-plan creation remain restricted. Interrupted signing/freezing needs a durable SDK-side build-intent/result contract, explicit fee/destination authorization, identity-preserving funding-signature support (including original passkey wallets), and restart recovery before exposing those operations. Existing signed plans/backups remain preserved. Returning a restriction is not completion of this requirement.
2. **Incoming claims and actual Spark settlement:** prove observation-only refresh, incoming claim authorization/fee ceilings and sender/receiver finality against real Spark operators and Lightning providers. The documented local cluster needs Docker, Rust and access to the private `ghcr.io/breez/spark-operator` image; that cluster was not available in this runtime. The Bitcoin node used here is not a substitute. Two disposable Spark wallets must prove exact sender debit, receiver credit and zero fee, then restoration on a separate device. Do not use the attached personal node/wallet credentials or real-user funds as fixtures.
3. **Operational rollback cutover:** the artifact is a read-only containment reader, not a funds-enabled rollback wallet. It preserves data and can unlock the existing encrypted mnemonic locally. It refuses unlock under an old service worker. Production-origin cached-client/service-worker cutover, original passkey recovery and resumption under the repaired version still need a rehearsal. Do not clear site data, swap wallet identities or revert to a plaintext-only build.
4. **Independent and physical-device acceptance:** review the exact final source and compiled SDK/WASM, then test iPhone Safari/PWA, Android Chrome/PWA and cross-device restoration with authorized disposable funding. Desktop Playwright engines are useful evidence but are not physical devices or independent security sign-off.
5. **Release evidence:** require CI on the published combined tree, complete untranslated security copy and assess dependency advisories. The inherited dependency audit reported zero runtime advisories and ten development-tool advisories; it did not establish that all development-tool advisories were resolved. No deployment, merge into main or production interlock removal occurred here.
