# Wallet-bound email verification

Status: **validated activation release with the production backend enabled**, 26 October 2026. Live email verification, durable storage and browser checks are complete. This release enables the public email-verification and native-name client gates.

The current username integration uses [Breez-native custom-domain registration](native-lightning-domain-rollout.md). Its proxy reads this service's verified wallet records. Keep the older `GETYOURSATS_HANDLE_ENABLED` forwarding-alias route disabled.

The `Settings → Account identity → Verify email address` screen requires **server confirmation**. A user still needs their wallet keys, passkey or recovery phrase to access the Bitcoin wallet. Email verification does not replace those credentials.

## Architecture

- Breez Spark `sdk.getInfo().identityPubkey` is the wallet identity.
- A short-lived one-time server nonce is signed using Breez Spark `sdk.signMessage({message,compact:true})`; the backend verifies the exact secp256k1 wallet identity signature with Node's crypto module before sending mail or revealing account status.
- OTP codes are generated by CSPRNG, HMAC-hashed, expire after 10 minutes and permit at most five attempts; sending is rate-limited per wallet/email/IP and uses provider idempotency keys.
- Challenge and verify limits use separate atomic fixed windows. One atomic send reservation checks the 80-attempt UTC daily budget, per-wallet/email/IP limits and a 60-second wallet/email resend cooldown before consuming any send allowance. Failed or uncertain provider calls still count because delivery may have occurred.
- Upstash Redis REST provides durable one-time challenges, OTPs and verified wallet↔email records; Redis Lua enforces atomic uniqueness of wallet and email ownership.
- Resend delivers plain-text verification codes. An account is marked verified only after the code is accepted and the server's atomic record update succeeds. All requests are same-origin HTTPS.
- The client never holds server secrets, and neither provider needs any recovery phrase or Lightning payment keys. Email never restores funds.
- Verified email makes the wallet eligible to request a native username. A separate user-initiated SDK claim and provider confirmation create the Lightning address.

## Deployment requirements

The Resend sending domain must remain verified with the required DNS authentication records. Keep the following values in the wallet's **server-only Vercel environment** for the intended deployment scope:

| Variable | Purpose |
| --- | --- |
| `UPSTASH_REDIS_REST_URL` | Durable email challenge, OTP and verified-account database |
| `UPSTASH_REDIS_REST_TOKEN` | Credential with the email service's required write, `GETDEL` and Lua access |
| `RESEND_API_KEY` | Domain-restricted verification email sending credential |
| `GETYOURSATS_EMAIL_FROM` | Sender approved for the verified domain |
| `GETYOURSATS_EMAIL_HMAC_KEY` | At least 32 random characters, generated and stored server-side |
| `GETYOURSATS_EMAIL_ENABLED` | Production is `true`; enables the configured email service |

None of these belongs in `VITE_*` or the browser bundle. Enter secrets directly in the provider environment. The Vercel integration's complete `KV_REST_API_URL`/`KV_REST_API_TOKEN` pair is also supported when neither explicit `UPSTASH_*` variable is present. An incomplete explicit pair fails closed rather than selecting a different database.

The wallet and root site use the same durable production database. The site prefers a read-only credential, while the email service needs writes and Lua scripts. Keep eviction and automatic upgrades disabled. Do not substitute an unclaimed temporary database for account records. Keep `GETYOURSATS_EMAIL_HMAC_KEY` stable: it determines the email-owner uniqueness index as well as OTP hashes, so rotation requires a planned index migration.

Maintain coverage for stale nonces, wrong signatures, replay, incorrect codes, restored status, reused email collisions, provider errors and throttling. Keep public privacy and retention notices aligned with the optional email service. Email address reassignment remains unavailable until an audited unlink/change flow exists. Simulated-recipient success establishes the tested API and OTP flow; it does not establish inbox placement across real email providers or all mobile browsers.

It rejects stale responses after a wallet change, validates the signing identity and never sends email on mount. Malformed stored records fail closed. ## Launch capacity

Custom names remain optional and eligible immediately after verified email. There is no deposit, transaction-count, volume or wallet-age requirement. The email allowance limits verification send attempts, not existing wallets, usernames or payments. Verified status is reused without another email and an existing valid code remains verifiable while new sends are paused.

Send throttling returns a reason code, UTC retry timestamp, remaining seconds and a `Retry-After` header. The screen shows the retry time in the user's local timezone, prevents repeated sends until then and keeps pending code entry available. Rejected capacity checks consume no send quota. Codes are generated only for an immediate send attempt; they are not queued overnight.

The daily application budget resets at midnight UTC (05:30 India time). Eighty attempts per day permits at most 2,400 sends in 30 days, with fewer successful first-time verifications when users resend or delivery fails. The current four-attempt per-wallet/email and eight-attempt shared-IP limits use 24-hour windows. They can affect group onboarding and should be reviewed against observed demand.

Resend's Free allowance is shared across the wallet and support form: 100 emails per UTC day and 3,000 per billing month. The 20-email difference is headroom, not a guaranteed support allocation. Support or other account activity can exhaust the provider allowance first. The provider's Free limit remains the final spending boundary; no paid tier or automatic upgrade is enabled by this integration.

Review capacity after sustained demand of roughly 50 to 60 verification sends per day or repeated capacity errors. This is an operational review trigger, not a user eligibility threshold. Any provider migration or paid upgrade requires a separate decision.

Provider references: [Resend quotas](https://resend.com/docs/knowledge-base/account-quotas-and-limits) and [Resend pricing](https://resend.com/docs/knowledge-base/what-is-resend-pricing).

## Readiness and recovery

If required configuration is missing or the service is disabled, `GET /api/account/email` returns `available:false` and the UI explains that verification is unavailable. This readiness response checks configuration, not downstream provider health. Only a wallet-authenticated server response establishes verified status. Email verification does not automatically register a custom address and is not a wallet recovery factor.
