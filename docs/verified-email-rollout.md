# Wallet-bound email verification — staged server integration

Status: **draft, disabled unless verified provider infrastructure exists**, October 2026.

The current username integration uses [Breez-native custom-domain registration](native-lightning-domain-rollout.md). Its proxy reads this service's verified wallet records. Keep the older `GETYOURSATS_HANDLE_ENABLED` forwarding-alias route disabled.

The new `Settings → Account identity → Verify email address` screen requires **server confirmation**. This is deliberately not an email-as-wallet-login design: a user still needs their Bitcoin wallet keys/passkey/phrase.

## Architecture
- Breez Spark `sdk.getInfo().identityPubkey` is the wallet identity.
- A short-lived one-time server nonce is signed using Breez Spark `sdk.signMessage({message,compact:true})`; the backend verifies the exact secp256k1 wallet identity signature with Node's crypto module before sending mail or revealing account status.
- OTP codes are generated by CSPRNG, HMAC-hashed, expire after 10 minutes and permit at most five attempts; sending is rate-limited per wallet/email/IP and uses provider idempotency keys.
- Challenge, send and verify limits use separate atomic fixed windows. A shared 80-attempt UTC daily mail budget includes failed or uncertain delivery attempts, leaving room in the observed free-provider allowance for support mail.
- Upstash Redis REST provides durable one-time challenges, OTPs and verified wallet↔email records; Redis Lua enforces atomic uniqueness of wallet and email ownership.
- Resend delivers plain-text verification codes. An account is marked verified only after the code is accepted and the server's atomic record update succeeds. All requests are same-origin HTTPS.
- The client never holds server secrets, and neither provider needs any recovery phrase or Lightning payment keys. Email never restores funds.
- Username/Lightning address claiming remains a separate entitlement, not activated by email alone.

## Activation prerequisites (owner-controlled)
- Verify a sending domain/subdomain for GetYourSats with Resend. DNS records and DKIM/SPF must be set in the **domain owner** Vercel DNS interface.
- Provision a durable Upstash Redis REST database with restricted write access and set the following **server-only Vercel Environment Variables**, in Preview/Production only as appropriate:
  - `UPSTASH_REDIS_REST_URL`
  - `UPSTASH_REDIS_REST_TOKEN`
  - `RESEND_API_KEY`
  - `GETYOURSATS_EMAIL_FROM` (verified sender e.g. `GetYourSats <verify@notifications.getyoursats.com>`)
  - `GETYOURSATS_EMAIL_HMAC_KEY` (minimum 32 random characters generated and stored server-side)
  - `GETYOURSATS_EMAIL_ENABLED=true` **only after real verification QA and security review**
- None of these belongs in `VITE_*` or the browser bundle. No secrets should be sent in chat.
- The Vercel integration's complete `KV_REST_API_URL`/`KV_REST_API_TOKEN` pair is also supported when neither explicit `UPSTASH_*` variable is present. An incomplete explicit pair fails closed rather than selecting a different database.
- Connect the same durable production database to the wallet and site. Disable eviction. The site prefers a read-only credential; the email service needs writes, `GETDEL` and Lua scripts. Do not use an unclaimed temporary database for account records.
- Keep `GETYOURSATS_EMAIL_HMAC_KEY` stable. It determines the email-owner uniqueness index as well as OTP hashes, so rotation requires a planned index migration.
- Test via a mainnet wallet with zero funds, verify stale nonce, wrong signature, replay, incorrect code, status after reload, reused email collision, provider errors, throttling, SMTP deliverability, supported mobile browsers, deletion/right-to-erasure and account recovery policy.
- Update public Privacy Policy regarding email PII processing and retention. Design an audited email unlink/change flow before allowing address reassignment.
- Require independent security review before enabling email accounts in production. Server code/unit tests alone are not certification.

## Configured preparation

The existing `getyoursats.com` Resend sending domain is verified. A dedicated domain-restricted sending credential, `GetYourSats <verify@getyoursats.com>` sender and generated server HMAC secret are configured in the wallet's Production environment. `GETYOURSATS_EMAIL_ENABLED` remains `false`. Durable Redis provisioning and real provider delivery/verification checks remain pending.

The client restores verified status only after signing an exact wallet-bound server challenge. It rejects stale responses after a wallet change, validates the signing identity and never sends email on mount. Malformed stored records fail closed. Duplicate mailbox ownership is checked atomically after a valid OTP, avoiding a mailbox-enumeration response before ownership is proven.

## No false claims
If the service isn't configured, `GET /api/account/email` returns `available:false` and the UI says email verification isn't active. Do not use browser storage to claim verified email. It is not yet a custom `@getyoursats.com` address, nor an account recovery factor.
